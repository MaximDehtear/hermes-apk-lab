## Code additions

### Static reconnaissance and exact references

New module `apk_lab/research.py`, CLI commands:

```bash
apk-lab recon JOB
apk-lab xrefs JOB 'Lpkg/State;->enabled:Z'
apk-lab xrefs JOB 'Lpkg/Settings;->refresh()V'
```

`recon` creates analysis/recon.json: app components, intent filters, permissions,
application/component attributes, smali/method counts, native method samples,
native libraries, framework hints and decompilation status. Implicit exported
is not replaced with false. Invalid XML produces a clear error. The report is
bound to the original SHA-256 and current-tree manifest hash.

`xrefs` scans all smali directories, including additional DEX. For an exact method
or field descriptor it saves call/read/write references with file, line, class,
method, instruction and source SHA-256. Comments, string literals and partial
matches are excluded. Full results go to JSONL; parameters/summary to adjacent
.meta.json; output contains the first 20 references. Results stay in the Hermes job.

These are exact static references, not a full call graph or proof of reachability.
Dispatch, reflection, JNI, dynamic code and special invoke forms require separate
investigation. Native declaration samples are limited to 200.

### APK integrity before installation and completion

Previously, install-test did not compare the builds APK with its saved verification
record, and finish relied on job/scenario records: a file modified after build
could diverge from saved evidence.

Now verified_build compares path/current SHA-256 with verification.json and checks
successful signature/alignment statuses. It runs before ADB and patch completion,
including none mode. finish additionally rejects stale SHA-256 in job state and
holds an operation lock. inspect checks the unchanged original before external commands.

Local JSON records are not protected against deliberate edits by the file owner.
The controller checks artifact consistency; interpretation of observations and
truthfulness of the verdict remain the investigating agent's responsibility.

## Investigation methodology improvements

- Start with observable acceptance criteria and scope.
- Map entry point, interface, callback, state, storage, network and JNI; separate
  app logic from SDK logic.
- Record hypothesis evidence, alternatives and a disconfirming experiment.
  Separate static conclusions from runtime observations, confidence from severity.
- Preserve a baseline, trace reads/writes/reset paths, check the diff and semantics
  of the re-decoded signed APK.
- Test relevant lifecycle/refresh/reset and neighboring behavior. Compilation,
  installation or the first screen is not a verified patch.
- Account for alternative persistent-state writers and SQLite WAL; keep diagnostic
  debuggable builds separate from the final APK.
- Bound negative network findings by observation conditions. A URL, permission,
  log marker or screenshot alone proves neither transmission nor its absence.
- Add native/JNI, Unity, Flutter, React Native and split routes, plus a report
  template with reproducible steps and evidence.
